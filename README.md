# Kenya Financial Analytics

A Kenyan-market quantitative finance workspace covering foreign exchange, government Treasury bills, bond valuation, options, portfolio construction, research, risk and strategy testing.

## Current deployment

- React / Next.js application on Vercel
- Preview environment: generated by the `vercel-react-migration` branch
- Existing Streamlit application retained as the reference implementation until the migration is fully verified
- Neon PostgreSQL used for persistent CBK observations

## Workspaces

The interface contains sixteen separate workspaces, each with a distinct analytical purpose:

| Workspace | Purpose |
|---|---|
| Dashboard | Service status, recent FX observations and latest matched auction curve |
| Kenyan Market | One currency pair's historical rate, returns and drawdown |
| Market Intelligence | Comparative FX moves and realised volatility |
| Yield Curve | Latest available matched Treasury-bill curve and tenor spread |
| Treasury Bills | Tenor-specific auction history and investment-yield price calculator |
| Bond Pricing | Coupon-bond price, duration, convexity and scheduled cash flows |
| Options & Greeks | European Black–Scholes value and option sensitivities |
| Backtesting | Lagged moving-average rule test with entry/exit costs |
| Risk Analysis | Empirical FX VaR, expected shortfall and drawdown |
| Risk Intelligence | Treasury-auction yield dispersion by tenor |
| Stress Testing | Capital and duration/convexity rate-shock scenarios |
| Portfolio Intelligence | Cross-pair returns, correlations and risk-return comparison |
| Portfolio | Weighted currency basket using aligned observations |
| Historical Market Explorer | Filter and export source observations |
| Research Intelligence | Moving-average trend research |
| Financial Reports | Source-aware market and auction summary |

## Data architecture

Persistent market observations are stored in Neon PostgreSQL.

- `fx_observations`: unique daily observations by date and currency pair
- `treasury_bill_observations`: unique auction observations by auction date and tenor
- `data_refresh_runs`: status and audit history for every market-data import attempt

The React API reads from Postgres. It does not present invented observations to fill gaps. Original CBK PDF extraction and FX parsing logic is retained and adapted for the hosted refresh function.

The scheduled Vercel function `/api/refresh` is configured for weekdays at 15:15 UTC (18:15 in Nairobi). It requires the sensitive `CRON_SECRET` and reads the Neon connection from `DATABASE_URL`. The scheduled importer is bounded to a small number of recent CBK auction PDFs per run to avoid overloading the source. A successful run records the result in `data_refresh_runs`; partial or failed runs are recorded distinctly.

## Security and privacy

- Secrets are stored as sensitive Vercel environment variables, not in source control.
- The public market endpoint is read-only.
- The ingestion endpoint is protected by a bearer secret.
- Browser security headers include CSP, HSTS, frame protection, MIME sniffing protection, referrer policy and permissions policy.
- The site stores only essential browser preferences; optional analytics and advertising trackers are not enabled.
- Privacy, terms and cookie notices are provided in the application.

## Local development

```bash
npm install
npm run dev
```

The Next.js application uses React, Recharts, Motion and Lucide. Python API dependencies are in `requirements.txt`. Dependencies for the retained Streamlit application remain in `requirements-streamlit.txt`.

## Important migration note

The migration remains staged. The Streamlit application and its original Python modules are preserved as the reference. The Vercel/React application should replace the public Streamlit link only after the production database refresh has been observed to succeed, the results are compared against the original implementation, and all remaining differences are resolved.
